# 0001. Межа доступу: база й сервер застосунку перевіряють доступ незалежно, обхід RLS — лише в схемі private

- Статус: прийнято
- Дата: 2026-10-27
- AC: AC-HOLD-08, AC-HOLD-40, AC-HOLD-42, AC-HOLD-44, AC-CARD-05, AC-CARD-06, AC-CARD-07, AC-CARD-08, AC-CARD-11

## Контекст

Картка клієнта — дані з обмеженим доступом (зріз 2).

- **Що бачать ролі:**
  - admin і scheduler бачать усіх клієнтів;
  - терапевт бачить лише «своїх» — з утриманням чи сеансом у нього (AC-CARD-05, AC-CARD-08);
  - без ролі й без входу не бачать нічого (AC-CARD-07, AC-CARD-11).
- **Розклад терапевта** показує ім'я клієнта без email (AC-HOLD-40). Інколи це ім'я клієнта, якого RLS `clients` терапевту
  вже не показує (AC-HOLD-42).
- **Відмова — з текстом PM і без даних.** Терапевт на сторінках планувальника отримує саме текст PM (AC-HOLD-44), а не
  порожній список. Спроба утримати слот чи створити картку в обхід сторінки має бути відхилена (AC-HOLD-08, AC-CARD-06).
- **Обмеження стеку (`AGENTS.md`):**
  - Supabase з Data API — браузер і сервер ходять у базу з ключем `publishable` і JWT користувача;
  - `SUPABASE_SECRET_KEY` у Vercel заборонено;
  - у supabase-js немає транзакцій;
  - `middleware.ts` замінено на `src/proxy.ts`.

## Рішення

Дві незалежні межі. Кожна сама по собі не віддає чужих даних.

1. **База — остання межа.**
   - **Кожна таблиця `public`:**
     - `enable row level security`;
     - `revoke all … from anon, authenticated`, далі лише явні `grant`, для `update` — колонкові;
     - політика на кожну операцію `to authenticated` з `(select auth.uid())`.
   - **Роль** — лише з `profiles.role` через хелпери `private.current_app_role()` і `private.is_staff()`.
   - **Обхід RLS** (запис із перевіркою, кілька таблиць разом, ім'я клієнта в розкладі) — лише функцією
     `security definer` у схемі `private` з `set search_path = ''`, перевірка ролі першим рядком (`hold_slot`,
     `confirm_hold`, `my_schedule`). Data API бачить лише тонку обгортку `security invoker` у `public`, `grant` — лише
     `authenticated`.
2. **Сервер застосунку — перша межа і текст відмови.**
   - **Сторінка `src/app/(app)/**/page.tsx`** першим викликає `getPageAccess()`: `getClaims()` → роль з `profiles`. Якщо
     доступу немає — `NoAccess` або `AccessDenied` з текстом PM, без жодного запиту даних.
   - **Server action** першим викликає `getCurrentUser()` (усередині — `getClaims()`), а вже потім звертається до бази.
   - `getSession()` для авторизації не використовуємо.
   - `src/proxy.ts` лише оновлює сесію: це зручність, а не захист.

Правила, які можна перевірити механічно, перевіряє `scripts/check-auth-boundary.mjs` (нижче).

## Розглянуті варіанти

- **A. Лише RLS, сторінки без перевірки ролі.** Простіше: одна межа.
  - Чому ні: RLS відповідає порожнім результатом, а не відмовою. Терапевт на `/holds` побачив би «No holds.» замість
    тексту PM (AC-HOLD-44), а без ролі — порожні сторінки замість пояснення (AC-CARD-11).
- **B. Лише перевірки в коді застосунку, база через `SUPABASE_SECRET_KEY`.** Звичний підхід «бекенд вирішує».
  - Чому ні: секретний ключ у Vercel заборонено (`AGENTS.md`, «Секрети»).
  - Одна забута перевірка в server action чи новому запиті віддає чужі картки. Data API з `publishable` ключем лишився б
    відкритим для будь-якого користувача з JWT.
- **C. View замість функцій `security definer`** для імені клієнта в розкладі терапевта.
  - Чому ні: view у `public` за замовчуванням виконується з правами власника й обходить RLS для всіх ролей. Він не може
    відмовити з кодом (`NOT_THERAPIST`) і не має параметрів тижня.
  - `security_invoker = true` повертає RLS `clients`, а саме вона ховає клієнта, чий слот уже почався (AC-HOLD-42).
- **D. Обидві межі (обрано).** Більше коду: перевірка ролі є і в застосунку, і в базі. Зате відмова має текст PM, а
  пропущена перевірка в одному шарі не відкриває даних.

## Наслідки

- **Простіше:** нову сторінку чи дію видно в рев'ю за шаблоном «доступ → дані». Тести бази на PGlite від імені кожної
  ролі не залежать від коду застосунку.
- **Складніше:**
  - роль перевіряється двічі;
  - зміна набору ролей — нова міграція хелперів і оновлення `src/lib/roles.ts`;
  - кожна функція `private` потребує обгортки в `public`.
- **Якщо специфікація зміниться** (нова роль, новий вид доступу), рішення лишається. Змінюються політики, хелпери ролей
  і `pageAccess`, а не межа.

## Як перевіряємо

- **`npm run check:auth`** (`scripts/check-auth-boundary.mjs`; у CI — job «Межа доступу: RLS, private і getClaims» у
  `.github/workflows/architecture.yml`). Вісім правил, вивід `файл:рядок: [правило]`, код виходу 1 на порушенні:
  - база: `definer-in-private`, `definer-search-path`, `table-rls`, `table-revoke`;
  - застосунок: `no-get-session`, `no-middleware`, `page-access` (getPageAccess до createClient / load…),
    `action-auth` (getCurrentUser / getClaims до `.from(` / `.rpc(`).
- **Самоперевірка правила** — `tests/scripts/check-auth-boundary.test.ts`. Чистий мінімальний проєкт проходить, а кожне з
  восьми правил має зламаний випадок, де падає саме воно. Сам репозиторій — без порушень.
- **Межа бази** — тести на PGlite від імені кожної ролі (`asUser`, `asAnon`) у `tests/db/`: `access.test.ts`,
  `client-access.test.ts`, `client-cards.test.ts`, `hold-rules.test.ts`, `my-schedule.test.ts`. Відмова на кожен AC
  відмови.
- **Межа сервера:**
  - `tests/page-access.test.ts` — рішення доступу за роллю;
  - `tests/holds-page.test.ts` і `tests/clients-page.test.ts` — сторінка з підміненим клієнтом: відмова без запиту даних.
- **Червоні прогони:**
  - мутації `grant` і політик RLS у PR #23, #24, #25 (падали тести бази);
  - мутація порядку «доступ → дані» на сторінці в PR цього правила (job `check:auth`).
